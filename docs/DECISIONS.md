# Amble — Decisions Log

Running log of choices made mid-build that aren't big enough for the Constitution but are still worth not re-litigating. Append-only, dated.

---

**[Locked pre-build] Task colors are semantic categories, not free-pick.**
Users choose from a fixed set of category colors (health, work, personal, admin, etc.) mapped through the Tier 2 token layer — not an open color picker. Keeps the timeline visually coherent and keeps colors swappable via re-theme without touching feature code.

**[Locked pre-build] State management is Riverpod, not Provider/Bloc.**
Chosen for closest fit to existing Zustand-style mental model (atomic, composable, testable without BuildContext threading) and good code-gen ergonomics with Claude Code sessions.

**[Locked pre-build] Editor/tooling: VS Code + Flutter/Dart extensions, Claude Code for implementation sessions.**
This chat (or equivalent) stays the architecture/planning layer; Claude Code in the actual project directory does file-by-file implementation.

**[Locked pre-build] Xcode 15.4 vs. 16+ — non-blocking.**
Works today, upgrade deferred to a "spare hour" task rather than a build blocker.

**[Phase 1] Riverpod providers use `keepAlive: true`, not `autoDispose`.**
Task CRUD state is session-scoped app state, not screen-scoped — `autoDispose` caused a real bug where a notifier's own write could be torn down mid-flight if no listener was active. Applies to `taskListProvider` and `taskByIdProvider`; default to `keepAlive` for any future app-level state provider unless there's a specific reason a provider should be screen-scoped.

**[Phase 1] `shared/providers/` added as a real folder, not just `features/*/providers`.**
Task CRUD state isn't feature-specific — it sits next to `shared/models/` and `shared/repositories/`, which it directly wraps. Feature-specific providers (if any arise) still belong under their own `features/*/` folder; this only applies to state that multiple features would otherwise duplicate.

**[Pre-Phase 3] Timeline scaffolding: custom-build the capsule blocks, allow a lightweight package for the date strip.**
The vertical day-timeline with capsule task blocks is the product's visual signature (per the Structured teardown and ARCHITECTURE.md's note on this being a design-taste problem as much as a code one) — building it on an existing calendar package (e.g. Syncfusion) would mean fighting the package's rendering/theming defaults to get the rounded, icon-overlapping capsule look, likely costing more effort than building custom on `CustomPainter`/`Stack` over the existing token system. The week/date strip at the top is a well-solved, non-differentiating pattern — a lightweight package there is fine if one saves real time, still subject to the "flag new dependencies" rule before adding.

**[Pre-Phase 3] Color primitives switched to OKLCH.**
Prompted by the clay/ochre category-color distinguishability concern flagged during Phase 2 review — hex/RGB doesn't guarantee two colors that read as "close" are actually perceptually close, OKLCH's perceptual uniformity does. Retrofit happens before Phase 3's capsule block work rather than after, since Phase 3 is about to make the current token values load-bearing across every timeline block. Implemented as a hand-written OKLCH→sRGB conversion (no new dependency — simple enough not to need one), applied only to color primitives; see ARCHITECTURE.md for the resulting `const` → `static final` deviation for that one token category. Category taxonomy (health/work/personal/admin) and its four accent hues are re-derived from OKLCH with deliberate hue/lightness/chroma spacing, not just re-hexed from the Phase 2 approximations.

**[Phase 3, Step 0] New category OKLCH values — needs review, not final.**
All four category accents fixed at equal L=0.70, C=0.13; hues spread 30°/120°/250°/340° (health/work/personal/admin) rather than naive 90° steps, specifically to avoid landing any pair on the red-green complementary axis (the classic protanopia/deuteranopia confusion line) — minimum pairwise hue gap is 50° (up from Phase 2's clay/ochre gap of ~35°), most pairs are 90°+ apart. The Phase 2 `moss500` (admin, dark yellow-green) is renamed `berry500` (magenta-pink) since re-deriving with proper spacing moved its hue far enough that the old name no longer describes the color — flagging the rename since it's a public token name, not just a value change. Confirmed visually via a debug build on iPhone 15 Pro Max simulator (`lib/features/timeline/timeline_capsule_preview_main.dart`, a scaffolding-only entry point) — all four colors read as clearly distinct at a glance.

**[Phase 3, Step 1] Capsule block badge-overlap padding bug, caught via simulator screenshot.**
The first capsule-block implementation positioned the icon badge correctly but under-computed the text content's left padding (used `badgeSize/2 + spacingSm` instead of `badgeSize + spacingSm`), so task titles rendered partially hidden behind the badge — invisible in `flutter analyze`/widget-test-without-golden, only caught by actually looking at a rendered screenshot. Flutter's headless `flutter test` golden rendering also doesn't load real fonts by default (renders text/icons as blank boxes), so the golden alone wasn't trustworthy for this review — confirmed the fix against a real debug build on the iOS Simulator instead, then regenerated the golden. If font-accurate goldens become worth the setup cost later, that's a `flutter_test_config.dart` + bundled font-loading addition, not yet done here.

**[Phase 3] Current-time indicator refreshes via a 1-minute `Timer.periodic`, not lifecycle events.**
The work order left refresh strategy as a judgment call (live vs. on-focus/resume). A periodic timer is simpler than wiring `AppLifecycleState` listeners and correct for the actual requirement — the line only needs to move once a minute, matching clock-face granularity. Scoped to `CurrentTimeIndicator`'s own `State` (started in `initState`, cancelled in `dispose`), so it only runs while the widget is mounted — no background timer leak risk. Revisit only if a real battery-cost concern surfaces; not expected at 1 update/minute.

**[Phase 3] Timeline day view opens scrolled to roughly the current time, not the top of the day.**
Added after reviewing the populated-day screenshot and finding the current-time indicator (correctly rendered) sat below the fold on load, at 5pm on a 6am–10pm view. A day view whose signature live element isn't visible without scrolling defeats the point of building it. Implemented via `ScrollController.jumpTo` in a post-frame callback in `_DayTimeline`'s `initState` — not requested explicitly by the work order but treated as directly in service of the current-time-indicator requirement, not scope creep.

**[Phase 3] `TaskCapsuleBlock`'s badge size is duplicated (not imported) in `timeline_screen.dart` for position math.**
The screen needs the badge's rendered size to convert "top of badge" positioning into "center of badge on the hour row" — but the badge size is an internal layout constant inside `TaskCapsuleBlock`, not part of its public API, and the component was explicitly kept unchanged this session. Mirrored the `spacingXl * 1.5` expression at the call site with a comment pointing back to the source of truth, rather than exporting a constant from the component or changing its interface. Worth promoting to a real shared constant (or a token) if a third call site ever needs it — per the "value used twice becomes a token" rule, this is the second use, so it's already a candidate.

**[Phase 3] Timeline golden test left stale through 3 rounds of visual iteration, per explicit instruction — now doubly stale.**
`test/features/timeline/timeline_capsule_preview_test.dart`'s golden was never regenerated across the two-column restructure, the badge/connector resize, or this session's alignment fix, since the work order said to hold until final sign-off on each round. It now fails `flutter test` with a large, expected pixel diff. Regenerating it is explicitly the first thing due whenever that file is next touched — noting here so a future session doesn't mistake the failure for a new regression.

**[Phase 4] `main.dart` replaced wholesale, not incrementally — Explore/Saved/Profile scaffold removed entirely.**
The scaffold mismatch (flagged repeatedly since Phase 0) had no real content worth preserving — placeholder pages with no data, no navigation logic tied to SCOPE.md's actual Inbox/Timeline/Settings structure. Replaced `AmbleHome`'s whole `IndexedStack`/`NavigationBar` shell with `Scaffold(body: TimelineScreen())` directly, no bottom nav yet. Bottom nav is deferred until Inbox (Phase 5) and Settings actually exist — building nav chrome for screens that don't exist yet would be exactly the kind of premature scaffolding CLAUDE.md warns against. `AmbleTheme.light` is now registered on `ThemeData.extensions` in `main.dart`, which the old scaffold never needed since it didn't consume Tier 2 tokens.

**[Phase 4] Completion/skip/reschedule status colors reuse the pre-existing, previously-unused `colorTaskCompleted`/`colorTaskSkipped` tokens — not the category color, and not a new "success green."**
Phase 2 defined these tokens speculatively; this session is their first real consumer. `completed` swaps the badge to `colorTaskCompleted` (sage, not the task's category color) plus a small checkmark overlay and a dimmed/strikethrough title — deliberately not the category color, so "done" reads as a distinct, calm state rather than "still that category, just also done." `skipped` swaps to `colorTaskSkipped` (neutral gray) rather than the previous alpha-blended category color, which is more correct token usage (a real semantic color, not a derived tint) and reads as more clearly "did not happen" without being punitive. `rescheduled` intentionally gets **no color change** — just a small neutral "moved" icon next to the time — per design principle 1 (no shame-coding); a rescheduled task is not a failed one, so recoloring it would misrepresent what the status enum is for.

**[Phase 4] Drag-to-reschedule snaps to 5-minute increments, tracked as a local `_dragOffset`, committed only on release.**
Continuous free-form dragging (no snap) would make it easy to schedule a task at :07 or :23, which doesn't match how the hour-marker grid or any real calendar UX reads. 5 minutes is fine-grained enough to feel responsive but coarse enough to always land visually aligned. The drag is purely a local widget-state visual (`_DraggableTaskBlockState._dragOffset`, reset to 0 on release) — nothing is written to the provider/repository until `onVerticalDragEnd`, so an aborted or accidental drag never touches persisted data. Reschedule logic itself (setting `originalScheduledAt` only once, moving `status` to `rescheduled`) lives in `TaskList.rescheduleTask` in the provider, not the UI — the widget only computes a `DateTime` and hands it off, per the "all writes go through taskListProvider" rule.

**[Phase 4] Real bug: `AppSheet`'s Cupertino branch had no `Material` ancestor — crashed the moment sheet content used a `TextField`.**
Caught while trying to screenshot the new task detail sheet, which was the first real (non-trivial) sheet content built since Phase 2 — `AppSheet`'s original test coverage only ever put a bare `Text` inside the sheet, on Material platform only, so this gap was invisible until now. `showCupertinoModalPopup` doesn't provide a `Material` ancestor the way `showModalBottomSheet` does implicitly; any Material-family widget (a `TextField`, in this case) inside Cupertino-branch sheet content throws "No Material widget found." Fixed by wrapping the Cupertino branch's content in `Material(type: MaterialType.transparency, ...)` inside `AppSheet` itself, so any future sheet content works on both platform branches without every caller needing to know about this. Also strengthened `design_system_scaffold_test.dart`'s sheet-content probe from a bare `Text` to a real `TextField`, and added a Cupertino-platform run of that same test — the Material-only, `Text`-only coverage is exactly why this didn't surface at Phase 2.

**[Phase 4] Task detail screen redesigned as a near-full-screen modal, not `AppSheet`.**
Per direct visual-reference feedback: a colored, edge-to-edge category header with an inline-editable title, a wheel-style time scroller, and a duration slider, presented almost full-screen (small gray gap at the very top, large corner radius) rather than `AppSheet`'s partial-height bottom sheet. Built as its own `PageRouteBuilder` (slide-up transition) inside `showTaskDetailSheet`, not through `AppSheet` — the colored, padding-free header doesn't fit `AppSheet`'s fixed white-background-plus-uniform-padding contract, and other, simpler future sheets should still get to use `AppSheet` as-is rather than inheriting this screen's specific visual needs. One form now serves both create and edit (previously discussed, confirmed with the user), pre-filled from the existing task when editing.

**[Phase 4] Two new adaptive `core/widgets/` components: `AppSlider`.**
The duration control needed a slider, and per design principle 4 (no raw `Material*`/`Cupertino*` in feature code), that meant a proper adaptive wrapper (`Slider`/`CupertinoSlider`), not an inline one-off in the feature file — added `AppSlider` alongside the existing `AppButton`/`AppSheet`/`AppIconButton`. `ListWheelScrollView` for the time picker was used directly (not wrapped) since it's a core Flutter widgets-library type, not Material- or Cupertino-specific, same class as `GestureDetector`/`Stack`.

**[Phase 4] Time scroller steps in 15-minute increments; duration slider steps in 5-minute increments, 5–120 min range — flagged, not derived from the reference.**
The reference screenshot's scroller showed 15-minute increments (17:30/17:45/18:00/...), kept as-is. The duration slider in the reference used discrete named steps (1/15/30/45m/1h/1.5h); per direct instruction this was intentionally *not* followed — replaced with a continuous 5-minute-step slider from 5 to 120 minutes instead, since a labelled multi-stop segmented control doesn't translate cleanly to a slider and 5-minute granularity is finer/more flexible.

**[Phase 4] Surface tokenization for the new gray-background/white-panel layout — flagged, not resolved.**
The redesigned detail screen introduces a "gray page background, white content panel" pattern (`colorSurfaceTimeline` reused for the gray, `colorSurfacePrimary` for the white panels) that doesn't yet have its own semantic name in `AmbleTheme` — it's borrowing two tokens whose original semantic intent was "timeline canvas" and "primary surface," not "elevated panel over a dimmed page." Works correctly today; flagged per the user's own call to defer a dedicated token (e.g. `colorSurfaceElevated`) rather than block this session on a token-system change.

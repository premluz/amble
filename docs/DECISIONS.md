# Amble — Decisions Log

Running log of choices made mid-build that aren't big enough for the Constitution but are still worth not re-litigating. Append-only, dated.

---

**[Locked pre-build] Task colors are semantic categories, not free-pick.**
Users choose from a fixed set of category colors (health, work, personal, admin, etc.) mapped through the Tier 2 token layer — not an open color picker. Keeps the timeline visually coherent and keeps colors swappable via re-theme without touching feature code.

**[Locked pre-build] State management is Riverpod, not Provider/Bloc.**
Chosen for closest fit to existing Zustand-style mental model (atomic, composable, testable without BuildContext threading) and good code-gen ergonomics with Claude Code sessions.

**[Locked pre-build] Editor/tooling: VS Code + Flutter/Dart extensions, Claude Code for implementation sessions.**
This chat (or equivalent) stays the architecture/planning layer; Claude Code in the actual project directory does file-by-file implementation.

**[Locked pre-build] Xcode 15.4 vs. 16+ — non-blocking.**
Works today, upgrade deferred to a "spare hour" task rather than a build blocker.

**[Phase 1] Riverpod providers use `keepAlive: true`, not `autoDispose`.**
Task CRUD state is session-scoped app state, not screen-scoped — `autoDispose` caused a real bug where a notifier's own write could be torn down mid-flight if no listener was active. Applies to `taskListProvider` and `taskByIdProvider`; default to `keepAlive` for any future app-level state provider unless there's a specific reason a provider should be screen-scoped.

**[Phase 1] `shared/providers/` added as a real folder, not just `features/*/providers`.**
Task CRUD state isn't feature-specific — it sits next to `shared/models/` and `shared/repositories/`, which it directly wraps. Feature-specific providers (if any arise) still belong under their own `features/*/` folder; this only applies to state that multiple features would otherwise duplicate.

**[Pre-Phase 3] Timeline scaffolding: custom-build the capsule blocks, allow a lightweight package for the date strip.**
The vertical day-timeline with capsule task blocks is the product's visual signature (per the Structured teardown and ARCHITECTURE.md's note on this being a design-taste problem as much as a code one) — building it on an existing calendar package (e.g. Syncfusion) would mean fighting the package's rendering/theming defaults to get the rounded, icon-overlapping capsule look, likely costing more effort than building custom on `CustomPainter`/`Stack` over the existing token system. The week/date strip at the top is a well-solved, non-differentiating pattern — a lightweight package there is fine if one saves real time, still subject to the "flag new dependencies" rule before adding.

**[2026-09-06] TaskTemplate's and TrackedBehavior's create/edit forms moved from `AppSheet` to `StepScaffold`, matching Task/Zone's near-full-screen presentation and Name-only-stage-1-then-reveal pattern.**
Requested directly: "add template and add tracked should follow same modal UI and interaction model as add task and add zone. Near full screen and disclosure first name and them reveal rest." Both forms now push the same `PageRouteBuilder` (slide-up, scrim barrier) as `task_detail_sheet.dart`/`zone_form_screen.dart`, gained an `_isNameStage` bool (true only on a fresh create; editing skips straight to stage 2), and stage their non-Name panes via the shared `AppStaggeredEntrance`. Name (and, where the model has one, Description/Notes) lives in one always-visible `AppPane` outside the staged block, matching `task_detail_sheet.dart`'s own "Name and Notes are never staged" convention — not a separate staggered pane, which an earlier draft got wrong before checking that convention. Reverses this feature's own earlier `AppSheet` choice (reasoned at the time as "four short fields don't justify a full-screen takeover"); that reasoning no longer holds once cross-flow consistency is the actual requirement.

**`TrackedBehaviorForm`'s `_AmountField` keeps its raw `TextField`, not `AppTextField`.** `AppTextField` has no `keyboardType` parameter, so switching it would silently drop the numeric keypad for amount entry. Kept as a deliberate, pre-existing exception (same pattern `behavior_outcome_prompt.dart` already uses), not new tech debt — flagged here so a future pass doesn't "fix" it into losing the numeric keyboard.

**[Pre-Phase 3] Color primitives switched to OKLCH.**
Prompted by the clay/ochre category-color distinguishability concern flagged during Phase 2 review — hex/RGB doesn't guarantee two colors that read as "close" are actually perceptually close, OKLCH's perceptual uniformity does. Retrofit happens before Phase 3's capsule block work rather than after, since Phase 3 is about to make the current token values load-bearing across every timeline block. Implemented as a hand-written OKLCH→sRGB conversion (no new dependency — simple enough not to need one), applied only to color primitives; see ARCHITECTURE.md for the resulting `const` → `static final` deviation for that one token category. Category taxonomy (health/work/personal/admin) and its four accent hues are re-derived from OKLCH with deliberate hue/lightness/chroma spacing, not just re-hexed from the Phase 2 approximations.

**[Phase 3, Step 0] New category OKLCH values — needs review, not final.**
All four category accents fixed at equal L=0.70, C=0.13; hues spread 30°/120°/250°/340° (health/work/personal/admin) rather than naive 90° steps, specifically to avoid landing any pair on the red-green complementary axis (the classic protanopia/deuteranopia confusion line) — minimum pairwise hue gap is 50° (up from Phase 2's clay/ochre gap of ~35°), most pairs are 90°+ apart. The Phase 2 `moss500` (admin, dark yellow-green) is renamed `berry500` (magenta-pink) since re-deriving with proper spacing moved its hue far enough that the old name no longer describes the color — flagging the rename since it's a public token name, not just a value change. Confirmed visually via a debug build on iPhone 15 Pro Max simulator (`lib/features/timeline/timeline_capsule_preview_main.dart`, a scaffolding-only entry point) — all four colors read as clearly distinct at a glance.

**[Phase 3, Step 1] Capsule block badge-overlap padding bug, caught via simulator screenshot.**
The first capsule-block implementation positioned the icon badge correctly but under-computed the text content's left padding (used `badgeSize/2 + spacingSm` instead of `badgeSize + spacingSm`), so task titles rendered partially hidden behind the badge — invisible in `flutter analyze`/widget-test-without-golden, only caught by actually looking at a rendered screenshot. Flutter's headless `flutter test` golden rendering also doesn't load real fonts by default (renders text/icons as blank boxes), so the golden alone wasn't trustworthy for this review — confirmed the fix against a real debug build on the iOS Simulator instead, then regenerated the golden. If font-accurate goldens become worth the setup cost later, that's a `flutter_test_config.dart` + bundled font-loading addition, not yet done here.

**[Phase 3] Current-time indicator refreshes via a 1-minute `Timer.periodic`, not lifecycle events.**
The work order left refresh strategy as a judgment call (live vs. on-focus/resume). A periodic timer is simpler than wiring `AppLifecycleState` listeners and correct for the actual requirement — the line only needs to move once a minute, matching clock-face granularity. Scoped to `CurrentTimeIndicator`'s own `State` (started in `initState`, cancelled in `dispose`), so it only runs while the widget is mounted — no background timer leak risk. Revisit only if a real battery-cost concern surfaces; not expected at 1 update/minute.

**[Phase 3] Timeline day view opens scrolled to roughly the current time, not the top of the day.**
Added after reviewing the populated-day screenshot and finding the current-time indicator (correctly rendered) sat below the fold on load, at 5pm on a 6am–10pm view. A day view whose signature live element isn't visible without scrolling defeats the point of building it. Implemented via `ScrollController.jumpTo` in a post-frame callback in `_DayTimeline`'s `initState` — not requested explicitly by the work order but treated as directly in service of the current-time-indicator requirement, not scope creep.

**[Phase 3] `TaskCapsuleBlock`'s badge size is duplicated (not imported) in `timeline_screen.dart` for position math.**
The screen needs the badge's rendered size to convert "top of badge" positioning into "center of badge on the hour row" — but the badge size is an internal layout constant inside `TaskCapsuleBlock`, not part of its public API, and the component was explicitly kept unchanged this session. Mirrored the `spacingXl * 1.5` expression at the call site with a comment pointing back to the source of truth, rather than exporting a constant from the component or changing its interface. Worth promoting to a real shared constant (or a token) if a third call site ever needs it — per the "value used twice becomes a token" rule, this is the second use, so it's already a candidate.

**[Phase 3] Timeline golden test left stale through 3 rounds of visual iteration, per explicit instruction — now doubly stale.**
`test/features/timeline/timeline_capsule_preview_test.dart`'s golden was never regenerated across the two-column restructure, the badge/connector resize, or this session's alignment fix, since the work order said to hold until final sign-off on each round. It now fails `flutter test` with a large, expected pixel diff. Regenerating it is explicitly the first thing due whenever that file is next touched — noting here so a future session doesn't mistake the failure for a new regression.

**[Phase 4] `main.dart` replaced wholesale, not incrementally — Explore/Saved/Profile scaffold removed entirely.**
The scaffold mismatch (flagged repeatedly since Phase 0) had no real content worth preserving — placeholder pages with no data, no navigation logic tied to SCOPE.md's actual Inbox/Timeline/Settings structure. Replaced `AmbleHome`'s whole `IndexedStack`/`NavigationBar` shell with `Scaffold(body: TimelineScreen())` directly, no bottom nav yet. Bottom nav is deferred until Inbox (Phase 5) and Settings actually exist — building nav chrome for screens that don't exist yet would be exactly the kind of premature scaffolding CLAUDE.md warns against. `AmbleTheme.light` is now registered on `ThemeData.extensions` in `main.dart`, which the old scaffold never needed since it didn't consume Tier 2 tokens.

**[Phase 4] Completion/skip/reschedule status colors reuse the pre-existing, previously-unused `colorTaskCompleted`/`colorTaskSkipped` tokens — not the category color, and not a new "success green."**
Phase 2 defined these tokens speculatively; this session is their first real consumer. `completed` swaps the badge to `colorTaskCompleted` (sage, not the task's category color) plus a small checkmark overlay and a dimmed/strikethrough title — deliberately not the category color, so "done" reads as a distinct, calm state rather than "still that category, just also done." `skipped` swaps to `colorTaskSkipped` (neutral gray) rather than the previous alpha-blended category color, which is more correct token usage (a real semantic color, not a derived tint) and reads as more clearly "did not happen" without being punitive. `rescheduled` intentionally gets **no color change** — just a small neutral "moved" icon next to the time — per design principle 1 (no shame-coding); a rescheduled task is not a failed one, so recoloring it would misrepresent what the status enum is for.

**[Phase 4] Drag-to-reschedule snaps to 5-minute increments, tracked as a local `_dragOffset`, committed only on release.**
Continuous free-form dragging (no snap) would make it easy to schedule a task at :07 or :23, which doesn't match how the hour-marker grid or any real calendar UX reads. 5 minutes is fine-grained enough to feel responsive but coarse enough to always land visually aligned. The drag is purely a local widget-state visual (`_DraggableTaskBlockState._dragOffset`, reset to 0 on release) — nothing is written to the provider/repository until `onVerticalDragEnd`, so an aborted or accidental drag never touches persisted data. Reschedule logic itself (setting `originalScheduledAt` only once, moving `status` to `rescheduled`) lives in `TaskList.rescheduleTask` in the provider, not the UI — the widget only computes a `DateTime` and hands it off, per the "all writes go through taskListProvider" rule.

**[Phase 4] Real bug: `AppSheet`'s Cupertino branch had no `Material` ancestor — crashed the moment sheet content used a `TextField`.**
Caught while trying to screenshot the new task detail sheet, which was the first real (non-trivial) sheet content built since Phase 2 — `AppSheet`'s original test coverage only ever put a bare `Text` inside the sheet, on Material platform only, so this gap was invisible until now. `showCupertinoModalPopup` doesn't provide a `Material` ancestor the way `showModalBottomSheet` does implicitly; any Material-family widget (a `TextField`, in this case) inside Cupertino-branch sheet content throws "No Material widget found." Fixed by wrapping the Cupertino branch's content in `Material(type: MaterialType.transparency, ...)` inside `AppSheet` itself, so any future sheet content works on both platform branches without every caller needing to know about this. Also strengthened `design_system_scaffold_test.dart`'s sheet-content probe from a bare `Text` to a real `TextField`, and added a Cupertino-platform run of that same test — the Material-only, `Text`-only coverage is exactly why this didn't surface at Phase 2.

**[Phase 4] Task detail screen redesigned as a near-full-screen modal, not `AppSheet`.**
Per direct visual-reference feedback: a colored, edge-to-edge category header with an inline-editable title, a wheel-style time scroller, and a duration slider, presented almost full-screen (small gray gap at the very top, large corner radius) rather than `AppSheet`'s partial-height bottom sheet. Built as its own `PageRouteBuilder` (slide-up transition) inside `showTaskDetailSheet`, not through `AppSheet` — the colored, padding-free header doesn't fit `AppSheet`'s fixed white-background-plus-uniform-padding contract, and other, simpler future sheets should still get to use `AppSheet` as-is rather than inheriting this screen's specific visual needs. One form now serves both create and edit (previously discussed, confirmed with the user), pre-filled from the existing task when editing.

**[Phase 4] Two new adaptive `core/widgets/` components: `AppSlider`.**
The duration control needed a slider, and per design principle 4 (no raw `Material*`/`Cupertino*` in feature code), that meant a proper adaptive wrapper (`Slider`/`CupertinoSlider`), not an inline one-off in the feature file — added `AppSlider` alongside the existing `AppButton`/`AppSheet`/`AppIconButton`. `ListWheelScrollView` for the time picker was used directly (not wrapped) since it's a core Flutter widgets-library type, not Material- or Cupertino-specific, same class as `GestureDetector`/`Stack`.

**[Phase 4] Time scroller steps in 15-minute increments; duration slider steps in 5-minute increments, 5–120 min range — flagged, not derived from the reference.**
The reference screenshot's scroller showed 15-minute increments (17:30/17:45/18:00/...), kept as-is. The duration slider in the reference used discrete named steps (1/15/30/45m/1h/1.5h); per direct instruction this was intentionally *not* followed — replaced with a continuous 5-minute-step slider from 5 to 120 minutes instead, since a labelled multi-stop segmented control doesn't translate cleanly to a slider and 5-minute granularity is finer/more flexible.

**[Phase 4] Surface tokenization for the new gray-background/white-panel layout — flagged, not resolved.**
The redesigned detail screen introduces a "gray page background, white content panel" pattern (`colorSurfaceTimeline` reused for the gray, `colorSurfacePrimary` for the white panels) that doesn't yet have its own semantic name in `AmbleTheme` — it's borrowing two tokens whose original semantic intent was "timeline canvas" and "primary surface," not "elevated panel over a dimmed page." Works correctly today; flagged per the user's own call to defer a dedicated token (e.g. `colorSurfaceElevated`) rather than block this session on a token-system change.

**[Phase 5] `Task.scheduledAt`/`durationMinutes` made nullable to represent unscheduled (Inbox) tasks.**
The model had no way to represent "captured but not yet scheduled" — both fields were required and non-nullable, and the Timeline's day-filter provider unconditionally dereferenced `scheduledAt`. Considered a sentinel-date hack (rejected — violates "no magic values" and creates real collision/ambiguity risk) versus nullable fields plus a derived `isScheduled` getter. Chose the nullable-field approach (confirmed with the user via AskUserQuestion rather than guessing, per CLAUDE.md). Added `Task.captured({title, notes})` as a second factory alongside `Task.create(...)`, title-only per design principle 2, defaulting `category` to `TaskCategory.personal` (changeable later when scheduled). `isScheduled` checks both fields are non-null (they're always set together — see `TaskList.scheduleTask`). Call sites that only ever see scheduled tasks (`TaskCapsuleBlock`, `TimelineScreen`'s positioning/drag math) use `!` rather than re-checking, since their callers (`tasksForSelectedDayProvider`) already guarantee it — documented in each with a doc comment rather than re-validated defensively.

**[Phase 5] Bottom nav built now — Inbox + Timeline, Settings still deferred.**
Phase 4's decision deferred all bottom nav chrome until Inbox existed (see above entries), on the grounds that scaffolding for screens that don't exist yet is exactly the premature-scaffolding CLAUDE.md warns against. Inbox now exists; Settings (Phase 8) still doesn't, so the nav ships with two real destinations rather than a three-tab shell with a Settings stub. `AmbleHome` (`main.dart`) wraps both screens in an `IndexedStack` behind a Material `NavigationBar`, defaulting to the Timeline tab on launch (index 1) to preserve prior default behavior. Add the Settings destination when Phase 8 gives it real content, not before.

**[Phase 5] Move-to-timeline reuses the existing task detail screen — no new scheduling UI.**
`TaskDetailForm`'s existing edit path (`existing.scheduledAt = _scheduledAt; existing.durationMinutes = _durationMinutes; ... updateTask(existing)`) already handles turning an unscheduled task into a scheduled one correctly — it just assigns real values to fields that were previously null, then persists via the normal update path. No changes were needed to `task_detail_sheet.dart` for this. `TaskList.scheduleTask(task, {scheduledAt, durationMinutes})` was still added to the provider as a named, intent-revealing entry point for any future non-UI caller, even though the sheet itself doesn't need it.

**[Phase 6] Exit-confirmation "worth asking" threshold: non-empty title AND at least one field (including the title itself) changed from its starting value.**
The work order asked for the threshold to be flagged, not guessed. Landed on: closing via the × button prompts only if the title is non-empty *and* something differs from where the form started (the task's saved values on edit, the pre-filled defaults on create) — checked against a snapshot taken in `initState` (`_initialTitle`/`_initialScheduledAt`/`_initialDurationMinutes`/`_initialCategory`/`_initialNotes`). Title counts as one of the tracked fields, not just a gate — typing a title from empty is itself "a field touched from its default," so a bare "typed a title, hit close" (the most common real case, e.g. from Quick Capture) does trigger the prompt. An empty title short-circuits to a silent close regardless of other fields, since no save is possible either way. Caught via the widget test in `test/features/task_detail/exit_confirmation_test.dart`: an earlier version only diffed the non-title fields, so typing a title alone never prompted — a real bug, not a spec ambiguity, fixed before considering the feature done.

**[Phase 6] Edit-flow close uses "Discard changes" / create-flow close uses "Delete draft" — same dialog, different secondary-button label and semantics.**
Confirmed with the user rather than guessing: an edit-flow close isn't discarding a draft, it's declining to save changes to an already-persisted task, so the destructive-styled button reads "Discard changes" and — critically — its handler is just `Navigator.pop()` (no delete call), leaving the previously-saved task exactly as it was. Create-flow close (nothing persisted yet) keeps "Delete draft," semantically a true discard, though it's the same no-op `Navigator.pop()` under the hood — the two paths only differ in what's already on disk, not in the code executed. Distinguished via `widget.task != null` (`isEditing`) inside `_handleClose`.

**[Phase 6] New adaptive component: `AppAlertDialog`.**
No existing two-choice confirmation dialog existed in `core/widgets/` — `showDialog`/`showCupertinoDialog` had never been used anywhere in the app. Added `AppAlertDialog.show(...)` (Cupertino `CupertinoAlertDialog` / Material `AlertDialog`, mirroring `AppSheet`'s platform-branching pattern) rather than reaching for a raw platform dialog inline, per design principle 4. Takes a primary and secondary `AppAlertDialogAction` (label + `isDestructive`), returns `true`/`false`/`null` for primary/secondary/dismissed.

**[Phase 6] Real bug found via testing, not screenshots: `flutter test` hangs on real Hive I/O triggered from a tapped widget.**
Full root-cause and fix in `docs/ERROR_LOG.md` ("`flutter test` hangs indefinitely on real Hive disk I/O triggered from a widget interaction"). Notable because it was caught by writing a widget test *before* trusting an on-device screenshot of the "Discard changes" outcome — the screenshot alone (an empty Inbox after discard) was ambiguous between "discard worked correctly" and "discard accidentally deleted the task," and only the widget test's explicit `expect(box.values.single.title, 'Existing task')` assertion actually proved which one was true. The on-device scaffolds (`exit_confirm_schedule_main.dart`/`exit_confirm_discard_main.dart`) were then updated to seed a second, untouched Inbox item so the screenshots themselves became unambiguous too, but the widget test is what caught and confirmed correctness first.

**[Phase 7] Two new dependencies added for notification scheduling: `timezone` and `flutter_timezone`.**
`flutter_local_notifications`' `zonedSchedule` — the only API that survives device timezone/DST changes correctly — requires `timezone`'s `TZDateTime`. `timezone` itself has no way to detect the device's actual IANA timezone name, and `flutter_local_notifications`' own README names `flutter_timezone` as the standard companion for exactly this gap. Both confirmed with the user before adding, per CLAUDE.md's "no new dependency without flagging first" rule; a hardcode-UTC alternative was explicitly rejected (silently wrong times for every non-UTC user is not acceptable). `NotificationService.initialize()` calls `FlutterTimezone.getLocalTimezone()` once, then `tz.setLocalLocation(...)`, before the plugin is otherwise usable.

**[Phase 7] Notification scheduling lives in `shared/services/notification_service.dart`, called from `TaskList` (the provider layer) — never from feature/UI code.**
Matches the existing repository-pattern precedent (`TaskRepository`/`HiveTaskRepository`): `NotificationService` only knows "schedule a task's alert" / "cancel by id" / "sync" (cancel-then-reschedule-if-appropriate); it has no opinion on *when* those should happen. Every `TaskList` mutator (`createTask`, `scheduleTask`, `updateTask`, `rescheduleTask`, `toggleComplete`, `deleteTask`) calls into it right after the repository write, so a screen never has to remember to sync a notification itself — the same reasoning that already keeps all persistence behind `taskListProvider`. `captureTask` (Inbox capture) is the one mutator that doesn't call it: an unscheduled task has no start time to alert on, so there is nothing to sync.

**[Phase 7] `syncForTask` always cancels first, then re-schedules only if still appropriate — one function, correct for every write path.**
Considered separate `schedule`/`reschedule`/`cancel` call sites per mutator (mirroring each mutator's specific semantic), but a single idempotent "cancel whatever alert this task might have, then schedule a fresh one if it should have one" is simpler and can't drift out of sync with itself — there's no way to leave a stale alert behind, since every path (including toggling a task back from `completed` to `pending`) runs through the same function. `syncForTask` skips scheduling entirely if `status == TaskStatus.completed` (no reason to alert for a task already marked done) — this is the one piece of scheduling *policy* that lives in the service rather than being pushed back to `TaskList`, since it's a rule about the service's own responsibility ("don't alert for finished things"), not a task-writing decision.

**[Phase 7] Notification permission requested lazily on first schedule attempt, not at app launch.**
The work order left this as a judgment call. `NotificationService.initialize()` (called once from `main.dart` before `runApp`) sets all `DarwinInitializationSettings.request*Permission` flags to `false`, so iOS shows no prompt on cold start. The actual `requestPermissions`/`requestNotificationsPermission` call happens inside `scheduleForTask`, the first time a task is created or scheduled with a future `scheduledAt` — i.e. the first moment permission is actually needed, not before. If denied, `scheduleForTask` returns early and every other write path (`saveTask`, `_refresh`) proceeds normally; the app has no notification-permission-gated features, so there's nothing else to degrade.

**[Phase 7] Notification id derived deterministically from the task's UUID string via `hashCode & 0x7fffffff`, not a separate persisted counter.**
`flutter_local_notifications` requires an `int` id per notification; task ids are UUID strings. Hashing gives the same task the same notification id every time without persisting a second id anywhere, so cancel-then-reschedule (`syncForTask`) always targets the exact alert a given task previously had. The `& 0x7fffffff` mask keeps the result a non-negative 32-bit int (`String.hashCode` can be negative/64-bit on some platforms), which is what the plugin's Android channel expects. A theoretical hash collision between two different task UUIDs would mean one task's alert silently overwrites another's — accepted as negligible given UUID v4's collision space and no evidence any Dart `hashCode` weakness make this a realistic risk at this app's scale.

**[Phase 7] Tap-to-open routes to the Timeline day containing the tapped task, via a new `notificationTapProvider` — done this session, not deferred.**
The work order flagged this as "if reasonable this session." Implemented via `getNotificationAppLaunchDetails()` (cold start) and `onDidReceiveNotificationResponse` (foreground/background tap) in `NotificationService`, both funneling the tapped task's id into a small keepAlive `NotificationTap` notifier. `AmbleHome` (`main.dart`) is the single place that reacts to it (`ref.listen`): looks up the task via the existing `taskByIdProvider`, calls `selectedDateProvider.notifier.goTo(scheduledAt)`, switches to the Timeline tab, then consumes the pending tap so it can't re-fire on a later rebuild. No new navigation infrastructure — reuses the existing bottom-nav `_selectedIndex` and the existing day-navigation provider.

**[Phase 7] Android manifest additions: two `flutter_local_notifications` receivers plus `RECEIVE_BOOT_COMPLETED`/`SCHEDULE_EXACT_ALARM`/`POST_NOTIFICATIONS` permissions.**
Taken directly from the plugin's own README (see `~/.pub-cache/.../flutter_local_notifications-22.3.0/README.md`), not guessed: `ScheduledNotificationReceiver` and `ScheduledNotificationBootReceiver` are required for scheduled alarms to actually fire and to survive a device reboot; `SCHEDULE_EXACT_ALARM` is the Android 12+ permission `requestExactAlarmsPermission()` requests at runtime, needed for `AndroidScheduleMode.exactAllowWhileIdle` (chosen over `inexact*` modes since a task-start alert that can silently arrive minutes late defeats the point). Notification icon reuses the existing `@mipmap/ic_launcher` rather than adding a dedicated drawable resource — a documented, valid option, just not Android's "official" preference; flagged in code as a candidate to revisit if a dedicated icon is ever designed. No R8/ProGuard `keep.xml` added, since the project has no release-build minification configured yet (`minifyEnabled` absent from `android/app/build.gradle.kts`) — worth adding before a real release build per the plugin's own warning that R8 can silently strip the icon resource otherwise.

**[Phase 7] iOS: `AppDelegate.swift` gained `FlutterLocalNotificationsPlugin.setPluginRegistrantCallback` inside the existing `didInitializeImplicitFlutterEngine`.**
Required per the plugin's README so plugin channels stay available if a notification action ever runs on iOS's background isolate — not currently used this session (no notification actions, only a plain tap-to-open), but it's the documented setup step and costs nothing to have in place now rather than being a silent gap discovered later. No other iOS-side native code was needed; permission requests and scheduling are handled entirely through the Dart-side plugin API.

**[Phase 6 closure] Android: `android/app/build.gradle.kts` gained `isCoreLibraryDesugaringEnabled = true` plus a `coreLibraryDesugaring` dependency.**
A genuine gap left by Phase 6, not an intentional deferral — `flutter_local_notifications` requires core library desugaring on any `minSdk` below 26 (this project's is 24), and Android had never actually been built with the notifications plugin present until this session, so the build failure only surfaced now. Fixed exactly per the plugin's own documented Kotlin/`build.gradle.kts` recipe (`desugar_jdk_libs:2.1.4`), not improvised. `multiDexEnabled` (also mentioned in the same README section) was deliberately *not* added — nothing in this build indicated the 64K method-count limit was actually being hit, and adding it speculatively would be exactly the kind of "design for a hypothetical future requirement" CLAUDE.md warns against; add it if and when a real build actually needs it.

**[Phase 6 closure] Android verification used a fresh local emulator (API 34, `google_apis/arm64-v8a`), not a physical device — no physical Android device was available.**
Created via `avdmanager` (`Amble_Test_API34`, Pixel 6 profile) since no AVD existed on this machine yet. API 34 (Android 14) chosen specifically because it's comfortably past API 33, where `POST_NOTIFICATIONS` became a runtime-requested permission — the exact behavior this session needed to confirm. Plain `google_apis` (not `google_apis_playstore`) to avoid Play Store account/approval friction that isn't relevant to this verification. `adb shell input tap`/`dumpsys notification`/`dumpsys alarm` gave direct, scriptable evidence of real permission-prompt delivery, notification content, and exact-alarm registration — a materially stronger verification path than was available on iOS Simulator last session (which had no equivalent to `adb`, hence the `DeliveredNotifications.plist` workaround documented in `docs/ERROR_LOG.md`).

**[Phase 7 (export/import)] Export/import serialization is hand-written `toJson`/`fromJson` on `Task`, no `json_serializable`.**
The model is small (10 fields) and stable; codegen for this one model would be a new dev-dependency (`json_serializable` + `build_runner` codegen step, on top of the `riverpod_generator`/`hive_ce_generator` already in the build) for marginal benefit. Both directions validate explicitly rather than trusting types: `fromJson` throws `FormatException` for any missing/wrong-typed/unrecognized field (including enum values that don't match `TaskCategory`/`TaskStatus`, and malformed ISO-8601 date strings), so a corrupt or hand-edited backup file fails loudly and specifically rather than constructing a partially-wrong `Task`.

**[Phase 7 (export/import)] Import conflict handling: skip + report, never silently overwrite. Confirmed with the user rather than assumed.**

Identical → counted as `alreadyPresent`, not rewritten (avoids a needless Hive write). Different → counted as a `conflict` and left completely untouched; the work order's own instruction was explicit that import must never silently corrupt or overwrite existing data, and building a real merge-resolution UI (which of two conflicting versions to keep, field by field) is a meaningfully larger feature than this session's scope — flagged as a genuine follow-up, not built speculatively. `TaskList.importTasks` returns an `ImportResult` (imported/alreadyPresent/conflicts counts) so the UI can surface this without the caller needing to inspect individual tasks.

**[Bug fix, post-Phase 9] Task writes are now resilient to notification-sync failure — `TaskList._syncNotificationSafely` wraps every `syncForTask`/`cancelForTask` call.**

Removing the suppression from scaffolds only (never from `lib/main.dart`, which should stay clean) means any scaffold build is now obvious at a glance. Cost: the DEBUG banner appears in the corner of scaffold screenshots used for visual verification — accepted deliberately, since a corner ribbon is far cheaper than repeatedly re-diagnosing which build is on screen.

**[Timeline, post-Phase 9] Drag shows live start/end times; overlapping tasks render side by side rather than pushing each other — cascade replanning stays out of scope.**
Two related asks from the same request. (1) **Drag time labels**: while a task is dragged, `TaskCapsuleBlock` shows the would-be start time above the pill and the end time (start + duration) below it, via a new `dragPreviewStartsAt` parameter. Both the label and the eventual commit read from the same `_previewStartsAt`/`_snappedMinutesDelta` getters, so the time shown mid-drag can never disagree with the time actually saved — the previous code computed the snapped delta only at drop time.

(2) **Drop onto an occupied slot**: the request was to "push another one" out of the way, but SCOPE.md line 26 explicitly defers "cascade replanning logic (automatic reflow when a task runs over)" out of the MVP, and push-on-drop *is* that feature — so per CLAUDE.md this was a stop-and-confirm, not a judgment call. Presented three options (allow-and-show, block-the-drop, full cascade with a SCOPE.md amendment); user chose **allow the overlap and show it visually**. Rationale that made this the recommendation: a partial "push one task" behaviour is arguably worse than none, because A pushing B can leave B overlapping C — either you chain-resolve (full cascade, deferred) or you silently create a different clash while appearing to have handled it. Showing the clash also matches design principle 1 (the plan is provisional, not a verdict) and keeps replanning an explicit user act rather than something the app does behind their back.

Implemented as a new pure function, `layoutOverlappingTasks` (`features/timeline/task_overlap_layout.dart`), kept widget-free so it's unit-testable: it groups tasks into overlap clusters, then packs each cluster into the fewest columns that keep genuinely-overlapping pairs apart — a task reuses the first column whose previous occupant has already finished, so 9:00-10:00 / 9:30-10:30 / 10:00-11:00 needs two columns, not three. Column count is per-group, so one busy hour doesn't narrow the whole day. 10 unit tests cover the edge cases (touching-but-not-overlapping boundaries, fully-contained tasks, column reuse, input-order independence).

Two rendering details worth recording: overlapping pills are offset by a **fixed pill-width per column**, not a fractional width — an initial `FractionallySizedBox` attempt rendered nothing differently, because the pill is a fixed-width element inside the block's `Row`, so narrowing the *available* width leaves it exactly where it was (caught on-device, not by analyze/tests). And a task in any column but the last caps its text width to one pill-width (`maxTextWidth`), so titles ellipsize instead of running underneath the neighbouring column's pill.

**[Timeline, post-Phase 9] Current time labelled in bold in the hour gutter; the hour label it would collide with is suppressed.**
Requested directly: show the current time in bold, to the left of the red now-line, with space between the label and the line's dot. Implemented in `CurrentTimeIndicator` by putting the label in a `SizedBox` matching the timeline's `_hourGutterWidth` (passed in as `gutterWidth` rather than duplicated, so it can't drift out of alignment with `HourMarkers`' labels), followed by the existing dot and line. Rather than nudge one of them, `HourMarkers` gained an optional `hideLabelNear` — the hour label closest to the current time is simply not rendered, so the gutter reads as one column with "now" as its emphasised member. **[Phase 10 (TrackedBehavior data layer)] `TrackedBehavior` field shape as actually implemented — `timesPerWeek` as a plain int, and a constructor-enforced target invariant.**
Built to CONSTITUTION.md's shape with two implementation choices worth recording. **Frequency** is a bare `int timesPerWeek`, not a recurrence rule — the work order and SCOPE.md both explicitly rule out a general recurrence system, and naming the field for its unit (rather than a generic `frequency`) makes the limitation self-documenting at every call site instead of inviting someone to later overload it with a richer meaning. **The "targetAmount is null only when targetType is binary" rule from CONSTITUTION.md is enforced by an assert in the constructor**, not left as prose. The alternative (trusting callers) would let an invalid object — a `duration` behavior with no target — persist to Hive and surface much later as a confusing null dereference in UI that doesn't exist yet. An assert fails loudly at the moment of construction and costs nothing in release builds; it's covered by a test that asserts the rejection, so the invariant can't silently rot. `BehaviorTargetType` is its own file/typeId (4) mirroring how `TaskStatus`/`TaskCategory` are already split out, rather than nested in the model file.

**[Phase 10] Feature flag mechanism: a plain `const` in `lib/core/feature_flags.dart`, default off.**
The work order left the mechanism to my judgment and explicitly said a bool in `core/` is enough for MVP. Chose an `abstract final class FeatureFlags` with `static const bool trackedBehaviorEnabled = false` over the alternatives (a Riverpod provider, a Hive-persisted setting, remote config): nothing about this flag needs to change at runtime or per-user, a `const` is trivially greppable to find every gated entry point later, and it dead-code-eliminates cleanly. Deliberately **nothing reads it today** — no UI exists to gate, which is the intended state until Phase 11+. Documented in the file itself that the flag gates *UI entry points only*; the data layer is never "turned off," only dormant, per CONSTITUTION.md.

**[Phase 10] `Task.behaviorId`/`actualAmount` are included in `toJson` but treated as optional in `fromJson` — backward compatibility with pre-Phase-10 backup files.**
The two new fields are written on export (otherwise a backup would silently drop a task's behavior link), but read with a plain nullable cast rather than the explicit presence/type validation the required fields get. This is deliberate: every backup file exported before this session simply has no `behaviorId`/`actualAmount` keys, and those files must still import cleanly — validating them as required would have broken import for every existing user backup. A *wrong-typed* value still fails loudly via the cast, matching how `notes`/`durationMinutes` and the other optional fields already behave. Covered by a test that strips both keys from an exported map and asserts the import still succeeds.

**[Phase 10] Two Hive field numbers (10, 11) appended to `Task`; no existing field numbers touched.**
Hive adapters key on field number, so appending is the only safe way to extend a model that already has persisted data on real devices — renumbering or reusing a retired number would silently misread existing records. Both new fields are nullable with a null default and are declared *after* every existing parameter, so `Task.create` and `Task.captured` are untouched at every one of their call sites. Verified by running the full pre-existing suite (59 tests, unmodified) immediately after regenerating the adapter, before writing any new tests — it passed identically to the pre-change baseline, which is the specific check the work order called the real risk of the session.

**[Phase 11 (recurring tasks)] Generation runs at app launch only, not on Timeline load — confirmed with the user, not guessed.**
CONSTITUTION.md says instances are materialized "whenever the app opens or a relevant screen loads," which leaves the actual trigger open; the work order explicitly called this a real design call. Presented launch-only vs. launch+Timeline via AskUserQuestion; user chose **launch-only**. Rationale: generation writes real Hive rows, and the Timeline is currently a pure reader — adding a write path there would mean every day-swipe could trigger writes. With an 8-week window, a session would have to stay open for weeks before the window ran dry, which does not happen in practice. `main.dart` calls `taskListProvider.notifier.materializeDueRecurrences()` once after the boxes open and notifications initialize. Creating a recurring task *also* materializes its series immediately (inside `createTask`), so a new series appears on the Timeline right away rather than only after the next launch — that's a separate, deliberate call, not the launch trigger firing early.

**[Phase 11] `recurrenceWindowWeeks = 8`, a named constant in the generator, not a magic number.**
Per the work order. Eight weeks is far enough that swiping forward never hits the window edge in normal use, and small enough that an open-ended daily series costs ~56 rows rather than the unbounded set generating-to-`endDate` would produce for a rule with no end. The generator takes `windowWeeks` as a parameter defaulting to this constant, which is what lets the tests exercise small deterministic windows without touching production behaviour.

**[Phase 11] Duplicate prevention keys on the occurrence slot — `originalScheduledAt ?? scheduledAt` — not on current position. Corrected after seeing the wrong behaviour on-device.**
`generateRecurrenceInstances` collects the claimed slot of every already-persisted instance in the series and skips any computed occurrence matching one. Instant-based rather than date-based, since a weekly rule with several `daysOfWeek` can legitimately put two instances on one day.

The first implementation keyed on `scheduledAt` alone, and I documented the consequence as an accepted trade-off: moving an instance frees its original slot, which the next generation run refills. **On-device verification showed that reasoning was wrong.** The edit-mode screenshot showed two "Morning run" entries on the same day — the user's rescheduled 08:30 one *and* a regenerated 07:00 duplicate. A user who reschedules one occurrence has not asked for a replacement to appear at the old time; that reads as the app undoing their edit. Fixed by preferring `originalScheduledAt`, which `TaskList.rescheduleTask` already preserves for exactly this "where did this originally belong" purpose (CONSTITUTION.md), falling back to `scheduledAt` for instances never moved. The regression test now asserts the moved-instance case generates **nothing**. Worth recording that the unit tests passed against the wrong behaviour too — they encoded my incorrect assumption, and only a real screenshot exposed it.

**[Phase 11] The series id is a fresh UUID, and only the template carries the rule.**
`createTask` mints a new UUID for `recurrenceId` when a rule is supplied. Every materialized instance carries that same `recurrenceId` with a **null** `recurrenceRule`, per CONSTITUTION.md — so "which task owns the rule" has exactly one answer (`isRecurrenceTemplate`), and `materializeDueRecurrences` finds series by scanning for templates rather than needing a separate index. Generation itself never persists: `generateRecurrenceInstances` is a pure function returning new `Task`s, and `TaskList` writes them through `TaskRepository` like every other mutation, so the "all writes go through the provider" rule holds.

**[Phase 11] Date arithmetic rebuilds from calendar parts rather than adding `Duration(days:)`.**
`DateTime.add(Duration(days: 1))` adds 24 hours of absolute time, which shifts the wall-clock hour by one across a DST boundary — a 09:00 daily task would silently become 08:00 or 10:00 for half the year. `_addDaysPreservingTime` constructs `DateTime(y, m, d + n, hour, minute, second)` instead, so the local time of day is preserved. Not hypothetical for a task app whose entire value is showing the right time.

**[Phase 11] Recurrence UI: an inline "Repeats" panel in the create form, collapsed by default and shown only when creating.**
Confirmed via AskUserQuestion (inline vs. a separate sheet); user chose inline. Deliberately **not rendered in the edit flow** (`if (widget.task == null)`): MVP edits affect a single instance only, so there is no series-level rule to edit from there, and showing a control that silently wouldn't apply would be worse than omitting it. `daysOfWeek` and `endDate` exist in the model and are fully supported by the generator and its tests, but are not yet exposed in the UI — flagged as the obvious next increment rather than built speculatively.

**[Phase 11] Recurrence indicator: a muted `repeat` icon beside the time, matching the existing "moved" indicator exactly.**

**[Phase 11] Editing/deleting one instance needed no special-casing — confirmed rather than assumed.**
The work order asked me to confirm this was naturally true. No sibling is reachable from those paths, so "this one only" falls out of the existing design rather than needing a guard. **[Phase 12 (cross-platform verification)] The import file picker IS drivable on Android via `uiautomator dump` — the "no tap tool" assumption was only ever true for iOS.**
Every prior session recorded the native file picker as unverifiable by an agent on *both* platforms (see the Phase 9 entry above). That was half wrong, and this session proved it by doing the thing. `adb shell uiautomator dump` returns the full on-screen view hierarchy **including other apps' UI** — so the picker's file rows can be located by their real `bounds` and tapped by computed coordinates, rather than guessed at. The correction worth recording is methodological: the earlier conclusion generalised an iOS limitation to Android without testing Android separately. **[Phase 12] Verification scaffold times are now anchored to the current hour rather than hardcoded to 07:00.**
`recurrence_verification_main.dart` seeded its tasks at a fixed 07:00/11:00. The Timeline auto-scrolls to "now" on open, so on any run after ~08:00 those tasks sat above the fold — invisible in a screenshot, and un-scrollable on iOS Simulator, which has no scroll gesture. Anchoring the seeds to `now.hour + 1` / `now.hour + 2` keeps both tasks in view on any platform at any time of day. **[Phase 12 (TrackedBehavior first UI slice)] The feature flag became a build-time override rather than being flipped to `true` — confirmed with the user.**
The work order left the mechanism open. Presented "build-time override, default stays off" vs. "flip the const to true"; user chose the override. `trackedBehaviorEnabled` is now `bool.fromEnvironment('trackedBehavior')`, which defaults to `false` when the define is absent — so an ordinary build (including any release build made from this commit) behaves exactly as it did before this UI existed, and SCOPE.md's "default off" stays honest without needing a code edit to keep it that way. Testing uses `--dart-define=trackedBehavior=true`. Because `bool.fromEnvironment` is const-evaluated, every `if (FeatureFlags.trackedBehaviorEnabled)` subtree still dead-code-eliminates in builds that don't opt in — the gate costs nothing at runtime.

**[Phase 12] The create-behavior form uses `AppSheet`, not Phase 4's near-full-screen modal.**
Phase 4 built the full-screen `PageRouteBuilder` pattern specifically for the task detail screen's colored edge-to-edge header, wheel time picker, and duration slider — none of which this form has. It's five short fields (title, type, target, minimum, times-per-week), so a full-screen takeover would be disproportionate and would imply more ceremony than the interaction deserves. `AppSheet` already handles the platform branching and the Material-ancestor fix from Phase 4, so this reuses a solved component rather than a solved *layout*.

**[Phase 12] Linking is available on both create and edit; recurrence remains create-only.**
These look similar but aren't. A recurrence rule defines a *series*, so editing it from one materialized instance raises the "this one or all future?" question that SCOPE.md explicitly defers — hence create-only. A behavior link is a property of *this single task* and nothing else, so changing it later is unambiguous and affects no sibling. The picker is therefore shown in both flows. Unlinking clears `actualAmount` in the same write: an amount measured against a behavior the task no longer belongs to would be orphaned data.

**[Phase 12] The outcome prompt is skipped for binary behaviors, on un-completion, and for dangling links — ordinary tasks never reach it at all.**
`_completeTask` in `timeline_screen.dart` guards in order: flag off → un-completing → no `behaviorId` → all take the original single-argument `toggleComplete(task)` path unchanged. Only a task that is being *completed*, is linked, and whose behavior is non-binary sees a prompt. Binary is excluded deliberately: "did it happen" is already answered by the completion itself, so asking would be friction with nothing to gain (design principle 2). A dangling link (behavior since deleted) also completes normally rather than blocking on a lookup that can't succeed. Dismissing the prompt still completes the task with `actualAmount` left null — declining to quantify is not declining to finish.

**[Phase 12] `toggleComplete` gained an optional `actualAmount`; un-completing clears it.**
The parameter is optional and omitted entirely by ordinary call sites, so ordinary completion is the same operation it always was — proven by the full pre-existing suite passing unmodified. Un-completing sets `actualAmount = null` because the amount described a completion that no longer stands; leaving it would misreport history the moment the task is completed again with a different result.

**[Phase 12] Recurring instances inherit `behaviorId` but never `actualAmount`.**
CONSTITUTION.md says the two systems compose without special-casing, so a series linked to a behavior means every occurrence is an instance of that behavior — the generator now copies the link onto each materialized instance. `actualAmount` is deliberately *not* copied: each occurrence records its own outcome, and inheriting one would fabricate evidence for days that haven't happened yet.

**[Phase 12] Indicator: a muted `track_changes` icon beside the time, matching the recurring indicator exactly.**
Same `colorTextSecondary` treatment as the recurring and "moved" indicators — being tracked is a neutral fact about a task, not a status worth colouring (design principle 1). A task can show both this and the repeat icon simultaneously, which is correct: the two systems are independent. Uses existing Tier 2 tokens only; no new tokens were needed.

**[Phase 13a (dark mode)] Preferences are a generic key-value store, not a theme-mode box.**
The work order called for this explicitly and it's the right shape: theme mode is the *first* preference to need persisting, not a special one. `PreferencesRepository` mirrors `TaskRepository`/`TrackedBehaviorRepository`'s interface style over a single untyped `preferences` box, with keys owned by `PreferenceKeys` so a read and a write can't diverge on a string literal. Later settings (default duration, week start, notification lead time) land here rather than each growing a box, adapter, and repository. `getValue<T>` returns null when the stored value isn't a `T` rather than throwing — a preference whose type changes between releases must degrade to its default, not make the app unlaunchable over a cosmetic setting.

**[Phase 13a] Theme mode is persisted as our own `AppThemeMode` enum (typeId 7), not Flutter's `ThemeMode`.**
Persisting a framework enum would tie the stored schema to Flutter's declaration order — a reordering upstream would silently reinterpret every stored value. `toFlutterThemeMode` in `preferences_providers.dart` is the single translation point. Provider is `keepAlive: true` per the Phase 1 precedent, and more strongly here than usual: the root `MaterialApp` is the only listener, so a screen-scoped provider would be wrong by construction. Defaults to `system` — a fresh install follows the OS rather than picking a side.

**[Phase 13a] Dark surfaces are a new `ink` OKLCH ramp at hue 90, not an inversion of the light palette.**
Derived the same way every other ramp here was (deliberate OKLCH triples — see the Pre-Phase 3 entry), not auto-darkened. Hue stays at 90, matching the `sand` neutral, so dark mode reads as the same product in low light rather than a generic grey theme. Two details that are deliberate rather than arbitrary: chroma is tiny (0.008–0.012) and *rises* with lightness, because at very low L a neutral needs almost no chroma to read warm and more makes surfaces look muddy; and the lightness steps are uneven (0.185 → 0.225 → 0.285 → 0.360) because perceived separation compresses near black, so equal steps would make the two darkest surfaces indistinguishable on a real screen. Two new `sand` entries (`sand200`/`sand400`) carry dark-mode text at a measured 15.6:1 and 7.5:1 against `ink900` — `sand50` blooms at that contrast and `sand500` doesn't clear comfortable secondary text.

**[Phase 13a] Category colors are unchanged for dark mode — measured, not assumed.**
Checked before deciding: at their current L=0.62/C=0.10 they land 4.9–5.2:1 against `ink900`, and the four hues stay as separable on dark as on light. Adding a dark-specific category ramp would have meant maintaining two sets of accent values for no measured gain, and would have edged toward the light-mode changes this session's non-goals rule out. Revisit in 13b only if they read as too saturated *in situ* rather than on paper.

**[Phase 13a] Material `ThemeData` seed and scaffold colors now derive from the palette instead of hardcoded hex.**
`main.dart` previously carried literal `0xFF5B6F52` and `0xFFF7F5F0` values — a no-magic-values violation, and a real hazard for dark mode specifically: the Material scaffold underneath our own tokens could disagree with them, leaving a light background peeking through a dark theme. `_themeDataFor(palette, brightness)` now reads `colorAccent`/`colorSurfacePrimary` off the palette, so a palette change propagates automatically and the two can't drift.

**[Phase 13a] System bar styling needs an explicit root `AnnotatedRegion` — no platform-specific code required.**
Worth recording because it's a non-obvious dependency: the app has no `AppBar` anywhere, and an `AppBar` is what normally manages status-bar icon brightness. Without this, dark mode renders dark status-bar icons on a near-black surface — invisible. Resolved against the *effective* brightness (`MediaQuery.platformBrightnessOf` for `system` mode), not the stored setting, so system-following works. One declaration covers both platforms: `statusBarBrightness` is iOS-only, `statusBarIconBrightness`/`systemNavigationBar*` are Android-only, and Flutter ignores the irrelevant ones per platform rather than erroring. Note the naming trap — `statusBarIconBrightness` is the *icon* colour while `statusBarBrightness` is the *background* it sits on, so a dark surface wants `Brightness.light` for one and `Brightness.dark` for the other.

**[Timeline, post-Phase 13a] Drag "lift" state: large shadow + slight scale + full opacity, replacing the previous opacity fade.**
Requested directly ("lift state on drag and drop, visually large drop shadow"). Confirmed the treatment via AskUserQuestion rather than guessing, since it replaces existing behaviour: the block previously faded to 0.75 opacity while dragging, which read as *receding* — the opposite of being picked up. It now stays fully opaque, scales to 1.04, and casts `shadowLift`.

The scale is deliberately small. A bigger lift reads more dramatically but makes the drop target ambiguous: the block stops matching the size of the slot it's about to land in, so the user loses the visual cue about where it will actually sit. 1.04 plus a large shadow carries the "raised" reading without that cost. Animated via `AnimatedScale` on the existing `motionFast`/`curveStandard` tokens so both the lift and the settle are visible rather than snapping.

**[Timeline, post-Phase 13a] `shadowLift` is a real Tier 2 token with a different value per palette, not an inline `BoxShadow`.**
This is the app's *second* shadow (the task detail sheet's sticky Continue button is the first), so per design principle 5 — a value used twice becomes a token — it gets promoted before a third use appears rather than after. Threading it through `AmbleTheme` means the constructor, both palettes, `copyWith`, **and** `lerp`; missing either of the last two would make the token silently revert to the other palette's value mid theme-animation, which is a bug that only appears during a transition and is very hard to spot by eye. Covered by tests for exactly that.

The per-palette split was confirmed with the user rather than assumed. Light uses `slate900` at 22% alpha; dark uses **pure black at 55%**. This isn't a tweak for taste — depth on a near-black surface has to come from something *darker than the background*, and the light shadow (tinted with the light-mode ink colour) is close to invisible against `ink900`. Both use the same geometry (`space9` blur, `space4` y-offset), which is deliberately larger than the Continue button's `spacingMd`/`spacingXs` so "lifted" is clearly distinguishable from the app's existing resting elevation — asserted in a test rather than left to drift.

**[Timeline, drag ghost] Ghost-rendering state moved from `_DraggableTaskBlock` to its parent `_DayTimelineState` — a real gesture bug, not a style preference.**
The first implementation had `_DraggableTaskBlock`'s `build()` return `Positioned.fill(child: Stack(...))` so a single widget could inject two `Positioned` entries (ghost + live block) into the ambient day-timeline Stack. This passed every check available short of a live drag: `flutter analyze` clean, full test suite clean, and a temporary magenta debug-marker widget confirmed the ghost's positioning math was correct. It still shipped a real bug, reported by the user: the first drag attempt on a fresh install would visually "arm" (shadow, scale, and preview time labels all appeared, proving `onVerticalDragStart` fired) but the block would not move, and only a second drag on the same task actually worked.

Root cause: `Positioned.fill` sizes its child to the *entire* ambient Stack's bounds, not to the block's own content — so every dragged task's wrapper had a hit-testable footprint the height of the whole day column while dragging, not just its own badge. The added Stack nesting (one more layer than the pre-ghost structure) combined with that inflated footprint disturbed gesture-arena arbitration on the first pointer-down after launch closely enough that the drag recognizer lost, evidenced by `onVerticalDragStart` firing while `onVerticalDragUpdate` never delivered real deltas.

Fixed by lifting "which task is currently dragging" to a new `_draggingTaskId` field on `_DayTimelineState`, and having the parent's existing `for (final slot in layoutOverlappingTasks(tasks))` loop emit the ghost as a genuine sibling `Positioned` — conditional on `_draggingTaskId == slot.task.id`, computed from the same `_minutesSinceStart`/column-offset math the live block already used — rather than nesting it inside the dragged widget's own Stack. `_DraggableTaskBlock` reports drag start/end via a new `onDraggingChanged` callback and is otherwise back to its exact pre-ghost shape: a single `Positioned` root, same nesting depth as before this feature existed.

Re-verified against the specific failure mode, not just re-derived structurally: force-stopped and relaunched the app, then dragged a task on the very first attempt post-launch — confirmed via a real `adb input draganddrop` mid-drag capture showing both the live preview labels and a visibly separate faded original-position element, with the drop landing correctly and no stuck lift/shadow state surviving either the drop or a subsequent app restart. Worth recording as a methodology note: "passes analyze, tests, and a structural debug check" is not the same bar as "works on a real interaction" — the gap here was gesture-arena behavior, which none of those three exercise.

**[Timeline] Day view widened from a fixed 6am-10pm window to the full 24-hour day — `_startHour`/`_endHour` constants, not a scroll fix.**

**[Cascade replanning] Push replaces reject-and-snap-back for the drag path only — a deliberate, confirmed reversal of the immediately-preceding decision, and a deliberate reversal of SCOPE.md's "explicitly out of MVP" line for cascade replanning specifically.** Confirmed directly by the user, as its own phase: `docs/SCOPE.md` now describes the implemented behavior in place of the old deferral line. The create wizard's Save/Schedule button and the edit-schedule modal's Save button (`task_detail_sheet.dart`) are untouched — both keep the exact reject-with-inline-error behavior from the entry above, since neither has a drag gesture to compute a push direction from, and a typed/picked time that overlaps should still just be rejected. Only `_DraggableTaskBlock.onDragEnd`'s rejection branch (`timeline_screen.dart`) changed.

**The push algorithm, derived by hand from two worked examples before any code was written** (per the work order's explicit instruction not to skip to UI wiring with an unverified algorithm) — full derivation and worked-example unit tests in `lib/shared/services/cascade_reschedule.dart` / `test/shared/services/cascade_reschedule_test.dart`. Direction: compare the distance from the dragged task's *new start* to the overlapped task's own start vs. its own end — whichever is nearer decides the push direction. Nearer-to-end → push the existing task **earlier**, its end landing exactly on the dragged task's new start (own duration preserved). Nearer-to-start → push the existing task **later**, but its new start lands on the dragged task's new *end*, not its start — because pushing later means the existing task now has to clear the mover's *entire* span, not just where it begins. This asymmetry is real, not an inconsistency: pushing earlier only needs to clear the mover's start (nothing after that start belongs to the mover from the earlier task's new position); pushing later has to clear the mover's end (the later task is now sitting immediately after the whole mover). Verified against both of the user's worked numbers: existing 11:00–12:00, drop at 11:45 (nearer end) → existing becomes 10:45–11:45 (the user's own restated "10:48" does not survive re-derivation from the stated rule and was treated as an arithmetic slip, per the work order's explicit warning not to trust a possibly-typo'd restatement — same category as the "12:115" the work order itself flagged as sic); existing 11:00–12:00, drop at 10:15 (nearer start) → existing becomes 11:15–12:15 (matches the user's own number once "12:115" is read as the stated typo for 12:15).

**Cascade chains via a simple BFS-style queue with a visited-id set, not recursion.** Each pushed task's new slot is checked against every remaining same-day task for a fresh overlap, which — if found — gets pushed the same way and queued to have its own new slot checked in turn. The visited set is both the cycle guard and the "never push the same task twice in one cascade" rule; chain length is additionally capped at the day's participating-task count, so a pathological input can't loop indefinitely even if the visited-set logic ever had a gap. Day-boundary guard (any move landing before 00:00 or after 24:00 of the day the dragged task started on) is checked per-move as the cascade builds, returning `null` the instant any move fails it — the caller then snaps the whole drag back untouched, exactly like the old reject behavior, so nothing partially applies.

**Persistence: a new `TaskList.rescheduleTaskWithCascade(List<TaskMove>)` provider method, not a UI-layer loop over the existing `rescheduleTask`.** Judgment call, flagged per the work order's explicit "make a call and justify it" instruction. Chose the provider-layer loop, following `_materializeSeries`'s precedent (loops and writes several tasks through `TaskRepository`, one `_refresh()` at the end) rather than `_DraggableTaskBlock` looping calls to the existing single-task `rescheduleTask`: a UI-layer loop would mean the widget makes N separate awaited provider calls, each triggering the notifier's own `_refresh()` and rebuilding the Timeline mid-loop — visually, every pushed task would appear to move one at a time rather than atomically, which contradicts the "applied atomically... pushed tasks just appear at their new positions after the drop completes" requirement. `rescheduleTaskWithCascade` looks each `TaskMove`'s task up fresh by id (mirroring `rescheduleTask`'s exact per-task semantics — `originalScheduledAt` set only once, `status` → `rescheduled`) and calls `_refresh()` once, after the whole cascade is written.

**`TaskMove` is a small paired class (`taskId` + `newScheduledAt`), not the `Task` object itself.** The cascade algorithm is pure and widget-free (`shared/services/`), so it never holds a live `Task` reference that could go stale between computation and the eventual write — the UI layer re-reads `ref.read(taskListProvider)` fresh right before computing the cascade, and `rescheduleTaskWithCascade` re-resolves each task by id from the repository immediately before writing it, the same pattern every other mutator in `TaskList` already uses.

**[Timeline] A drop onto a busy zone is never rejected — the cascade falls back to the opposite push direction instead.**
Requested directly, after observing drops snapping back in condensed zones: "should always allow to drop should not revert, can't think of case that should not be allowed to drop to a busy already taken zone, it'd just move other items up down or some up some down." Rejection is now reachable only when the day genuinely cannot hold the tasks: the dragged task itself landing outside 00:00–24:00, or a day packed near its full 24 hours (rare, given the 2h-per-task cap). **[Task detail] Removing a recurring task asks "this occurrence" vs "all occurrences"; "all" means this one plus everything from today forward.**
Requested directly. Previously Remove deleted a single instance with no confirmation at all, even for a series. Two scope questions confirmed via AskUserQuestion rather than assumed:

1. **Past instances are kept** on "all occurrences" — the series stops from today forward, history stays. **[Quick Capture natural-language parsing] Pure Dart, on-device, no external APIs — confidence threshold and highlighting approach flagged for review, per the work order.**

1. **Confidence rule (the auto-create gate): a parse is confident if and only if an explicit date/time anchor was matched** — a relative-day word (`today`, `tomorrow`, `next <weekday>`) or a clock time (`at 10:30`, `3pm`). A duration or recurrence phrase found with NO such anchor does NOT make the parse confident, even though something was extracted — flagged explicitly per the work order's own "every morning" example. Rationale: auto-create with no confirmation step is only safe when the resulting `scheduledAt` is the thing the user unambiguously typed, not an inference. When not confident, `durationMinutes`/`recurrenceRule` are both `null` in the result even if phrases matched — nothing partially leaks into a result the caller might treat as meaningful — and the ENTIRE raw input becomes the title untouched, exactly matching today's existing Quick Capture fallback.
2. **A relative-day word with no explicit clock time defaults the time-of-day to 09:00.** Flagged as an explicit placeholder choice, not a guess at intent beyond "this day" — duration defaults to `quickCaptureDefaultDurationMinutes` (30, matching the create-flow default) under the same reasoning.
3. **Live highlighting is implemented via a `TextEditingController` subclass overriding `buildTextSpan`,** not a stacked-overlay `RichText`-over-invisible-`TextField` approach. Flagged per the work order: this keeps cursor placement, selection, IME composition, and deletion entirely native, since there's only ever one real text-rendering object rather than two that must stay pixel-identical to each other. Re-parses on every `buildTextSpan` call — acceptable for Quick Capture's short, single-line input, not a pattern to reuse for a large multi-line document.
4. **Highlight colors: three EXISTING Tier 2 tokens, not new ones** — `colorAccent` (date/time), the WORK category's `categoryIconColors` entry (duration), `colorTaskAlert` (recurrence). Flagged mapping, since none of the three was originally named for this purpose, chosen for being saturated/distinguishable and not colliding with any category pill shown elsewhere in the same view.
5. **New adaptive component: `AppUndoToast`.** No existing snackbar/toast-style component existed. Deliberately NOT a Cupertino/Material platform branch — neither platform's native transient-message UI is being reached for directly, and a plain rounded card reads as "the app's own" chrome on both platforms, same reasoning `AppTextField` already applies to genuinely platform-neutral widgets. Self-manages its own `OverlayEntry` lifecycle (inserted on `show`, removed on expiry or on Undo). Uses `Overlay.of(context, rootOverlay: true)` — the app's outermost Overlay, not the nearest enclosing one — since this toast is shown immediately after a provider write that rebuilds the calling screen, and the root Overlay is the more robust target for anything meant to outlive that specific screen.
6. **Undo removes the whole series for a confident parse that also matched recurrence**, not just the one instance — `createTask` materializes a whole series immediately when a `RecurrenceRule` is supplied, so `AppUndoToast`'s undo calls `deleteTaskSeries` (not `deleteTask`) when the created task `isRecurring`.

**[Loading spinner] Save/create buttons show a spinner while the write is in flight, to stop double-taps from double-creating/editing a task.**

1. **Scope, confirmed directly via AskUserQuestion: Task Detail (create + edit) and Quick Capture's Add button only.** The retired `_EditScheduleForm`/`_EditDetailsForm` (dev-scaffold-only, unreferenced from real UI — see the recurrence-editing bug above) deliberately did NOT get this treatment; no reason to invest in dead code.

3. **Loading is visually distinct from plain-disabled, not the same washed-out grey.** A disabled button reads as "you can't do this"; a loading button just did exactly what was asked and is busy following through — so the fill/foreground keep their normal enabled colors, and only the label swaps for a small spinner (`CupertinoActivityIndicator` on iOS/macOS, `CircularProgressIndicator(strokeWidth: 2)` elsewhere), sized off the label's own `fontSize` so the button's height doesn't jump when it swaps in.

**The horizon is 14 days, deliberately shorter than the 8-week materialization window.** Tasks are still persisted 8 weeks ahead — the Timeline needs to render them — but only the near two weeks hold an actual OS alarm, topped up on each launch. This is what bounds the alarm count: previously a single daily recurring series registered ~56 alarms, and a handful of series exceeded Android's hard cap of 500, after which *every* `zonedSchedule` threw. 14 days is far enough that a normally-used app tops the window up long before a task falls due, and short enough to keep the count well under the cap even with many series. The trade-off, accepted explicitly: a task scheduled 3+ weeks out has no OS alarm registered at the moment it's created — it gets one on a later launch. Not a behavior change any user can observe unless the app is never opened for weeks, in which case the alarm was going to be unreliable regardless.

**`refreshScheduled` cancels ALL notifications before re-registering.** Considered tracking which ids fell out of the horizon and cancelling those individually; rejected as strictly worse — it needs bookkeeping that can drift, and it can't help an install that has *already* hit the cap (the stale 500 are still registered, so nothing new can schedule). `cancelAll()` then re-register is idempotent, self-healing, and needs no persisted state about what was scheduled last time. Cost is a burst of platform calls at launch, which is why it's not awaited before `runApp`.

**Notification sync is fire-and-forget on all ten `TaskList` write paths, not awaited.** The task is already persisted before the sync runs, and `_syncNotificationSafely` already catches and logs its own failures — so awaiting it only ever meant "make the user wait for something we've decided is allowed to fail." The principle: a side effect the code treats as optional must not sit on a user-visible critical path.

## [2026-09-04] Zone containment: TIME wins over an explicit `zoneId` when both are set

**Reverses** the original Spatial Zone View rule (`zoneId` authoritative, winning even over a conflicting `scheduledAt`). Confirmed directly via AskUserQuestion after the alternative options (clear `zoneId` on time change; keep the rule but show a mismatch cue) were put side by side.

**Reported symptom**: a task reading 5:15–17:15 in Task view rendered inside the 09:00–13:00 container in Zone view.

**Root cause**: `zoneId` is only ever SET, never cleared. `rescheduleTaskWithZone` (a Zone-view drop) assigns it; `rescheduleTask` (Task view's own drag) deliberately never touches it, and the task detail sheet never references `zoneId` at all. So any later time change stranded a stale assignment that then outranked the task's real time, and the two views disagreed about the same task.

**Resolution now**: if `scheduledAt` is set, the task places by time — into whichever zone's window contains it, or into no zone if it falls outside every one, regardless of `zoneId`. Only a zone-only task (no `scheduledAt`) places by `zoneId`, which is the case the "a task can be assigned to a zone with no scheduledAt at all" design note exists for. Still strictly read-only: nothing writes or clears `zoneId`, so a stale assignment simply stops affecting placement and stays on the row.

**Why this over clearing `zoneId` on time change**: that would need every current and future write path that touches `scheduledAt` to also maintain the assignment — exactly the kind of invariant that decays silently (this bug is what its absence already looks like). Resolving by time at read time cannot drift.

## Resize handles shrink on short blocks (2026-09-08)

`ResizeHandle` gained an optional `height`, and `resizeHandleHeightFor(theme:, blockHeight:)` computes it. Both `PendingTaskPill` and `TaskCapsuleBlock` now pass it.

The problem it fixes, flagged when the top-edge handle was added and left open for two rounds: a block gets a top and a bottom handle at `spacingMd` (16px) each, but a task at the 5-minute duration floor renders at `sizeTaskBadge` (24px). 32px of handle in a 24px block — the two handles overlapped, the block was entirely grab-to-resize, and it could not be dragged to a new time at all.

The helper returns the default height whenever the block can afford two of them plus a 12px move band, and otherwise shrinks both to whatever preserves that band — with an 8px floor, below which a handle stops being reliably hittable. Past that floor a cramped move band is the better trade than two handles too small to grab.

This is why `resizeHandleHeightFor` lives beside `ResizeHandle` rather than in either caller: both spatial blocks have the same geometry problem and must not drift apart on the answer.

## Quick-create scroll reserves room for the mini sheet (2026-09-08)

Reported directly: "bug when adding task quick add after 20:00 the sheet covers 20-24 hours so cant see."

## List mode zone bands now guarantee zoneBackgroundGap (4px) minimum separation (2026-09-08)

## Hour-boundary label clipping: the real fix was one layer further in (2026-09-08)

## [2026-09-09] Zone materialization — real per-occurrence instances, replacing the one-shot recurrence/notification workaround

Rearchitected `Zone` recurrence to mirror `Task`'s own materialized-instance pattern exactly (CONSTITUTION.md's "Recurring tasks — materialized instances, not virtual expansion"), per a work order requesting the same philosophy applied to Zone. Confirmed pre-launch/no-real-users, so no migration path was built for any existing recurring `Zone` data — a recurring zone created before this session has no `recurrenceId`/materialized instances and simply won't retroactively materialize; stated here rather than silently handled.

**Model**: `Zone` gains `recurrenceId: String?` (`@HiveField(7)`, series link, same shape as `Task.recurrenceId`) and `anchorDate: DateTime?` (`@HiveField(8)`). `isRecurring`/`isRecurrenceTemplate` getters mirror `Task`'s exactly. **Judgment call, confirmed via AskUserQuestion before building**: a non-recurring zone stays exactly as it was pre-session — one dateless row, `anchorDate == null`, applying to every day. Only a recurring series' instances (including its own template) carry a real `anchorDate`. The alternative (giving every zone, recurring or not, a date) was explicitly ruled out as unrequested scope broadening — it would have required rebuilding the "applies every day" behavior a plain one-off zone already has.

**Materialization**: new `shared/services/zone_recurrence_generator.dart` (`generateZoneRecurrenceInstances`), mirroring `recurrence_generator.dart`'s `generateRecurrenceInstances` structurally — same 8-week rolling window (`recurrenceWindowWeeks`, imported not duplicated), same per-day dedup-by-`anchorDate` idempotency, same daily/weekly occurrence-walking logic, simplified to bare calendar days since a Zone anchor carries no time-of-day of its own (only `startMinutes`/`endMinutes`, copied uniformly to every instance — per-day-varying times are out of scope this session, per CONSTITUTION.md's still-deferred fork). `ZoneList.createZone` materializes a new series' full window immediately on create (mirrors `TaskList.createTask`); `ZoneList.materializeDueRecurrences()` tops up every series' window, called from `main.dart` alongside the existing `TaskList` call.

**Notification scheduling deviates from a literal reading of the work order, flagged directly**: item 5 asked for "each materialized Zone instance schedules its own real notification on creation." Doing that literally would schedule an OS alarm for every one of up to ~56 instances per series at materialization time — exactly the Android 500-concurrent-alarm-cap bug CONSTITUTION.md's Task section documents fixing (see docs/ERROR_LOG.md). Mirrored `TaskList._materializeSeries`'s own discipline instead: materialization saves rows without scheduling; `ZoneList.refreshScheduledNotifications()` (already existed, already called from `main.dart`) registers alarms only for in-horizon instances. `NotificationService.scheduleForZone` was rewritten to resolve a materialized instance directly against its own `anchorDate` + `startMinutes` (exactly like `scheduleForTask` resolves `task.scheduledAt`) — no rule evaluation, no "next occurrence" search. `_nextZoneOccurrence`/the zone-side `_ruleMatchesDay` were deleted entirely, confirmed removable: every occurrence is now a real row with a real time, so there was nothing left to re-resolve. **Non-recurring zones are unaffected** — `scheduleForZone` still resolves them against today's date exactly as before.

**Fixed a pre-existing gap while here**: `ZoneList.deleteZone` never cancelled the deleted zone's notification (confirmed by reading the prior code — a genuine pre-existing omission, not something this session's changes caused). Added the `cancelForZone` call, since per-instance deletion becomes a routine operation once a series is many real rows rather than one shared one.

**Zone-to-zone overlap check, cascade, and containment all now filter to same-day instances rather than evaluating a rule** — the "should get simpler, not more complex" case from the work order. `zone_form_screen.dart`'s overlap validation filters candidate zones to `anchorDate == null || isSameDay(anchorDate, thisDay)` before calling the unchanged `zonesOverlap`. `zone_containment.dart`'s `_zoneAppliesOnDay` collapsed from a rule-evaluation function to a plain field comparison. `timeline_screen.dart`'s `_commitZoneCascade` (the shared commit path for both Zone-view and Task-view zone resize/move) now takes a `day` parameter and filters `otherZones` to the same day-membership rule before calling the (unchanged) `computeZoneCascadeMoves` — this is what makes resizing one occurrence leave every sibling occurrence in the same series untouched, verified end-to-end in a widget test (`zone_task_view_move_resize_test.dart`): two materialized instances of one daily series, resizing today's instance leaves the other's `startMinutes`/`endMinutes` completely unchanged.

**`Task.zoneId`/`resolveZoneContainment` interaction, confirmed compatible rather than assumed (item 6)**: containment already resolves by TIME first (the 2026-09-04 reversal), falling back to explicit `zoneId` only for a zone-only task with no `scheduledAt`. The only write site for `Task.zoneId` (`rescheduleTaskWithZone`, Zone-view drag-and-drop) already operates against a day-scoped zone list (`ZoneDayTimeline` receives zones already filtered to the viewed day). So once `zoneListProvider` returns materialized per-day instances, a drop on a given day's container already naturally sets `zoneId` to that day's specific instance id, not a shared series row — no code change was needed for this to hold. **One residual risk, not fixed, matching existing posture**: a zone-only task assigned to one recurring instance's id becomes orphaned if that specific instance is later pruned/deleted — the same "stale zoneId, never cleared" gap the 2026-09-04 decision already accepted for the non-recurring case, just now also reachable via series editing.

**Regression caught and fixed before it shipped, not part of the original work order**: the Spatial Task View's own zone-background rendering (`timeline_screen.dart`'s `zones` local, feeding `ZoneBackgroundBlock`) reads `zoneListProvider` directly and un-filtered by day, unlike Zone view (which already goes through `resolveZoneContainment`). Without a fix, every materialized instance of a series would render simultaneously overlapping on any single day, since they all share the same time-of-day window. Added the same day-membership filter at that single call site — confirmed as the right, minimal fix via a widget test that failed with 2 overlapping blocks before the fix and passed with exactly 1 after. **Settings → Zones list screen has the same shape of problem** (lists every row in `zoneListProvider` unfiltered) — confirmed via AskUserQuestion to filter to `!isRecurring || isRecurrenceTemplate` (one row per series, tapping it edits the template) rather than leaving it to show up to ~56 rows per recurring zone.

**Verification**: `dart format .` clean, `flutter analyze` clean (2 pre-existing unrelated warnings, unchanged). Full suite excluding `test/features/timeline/` (per this repo's standing convention for that known-hanging directory): 584 passed, 4 pre-existing failures confirmed unrelated by direct comparison (`zone_form_screen_test.dart`'s notification-permission test and 3 `slack_summary_settings_test.dart` network tests, all failing identically before this session's changes). `test/features/timeline/` run separately: confirmed the directory-wide hang is pre-existing (`list_mode_clustering_test.dart` "did not complete"), unrelated task-multi-drag test failures pre-date this session (no zone code in their path); every zone-relevant file in that directory run in isolation — `collapsed_zone_bands_test.dart`, `zone_day_timeline_move_resize_test.dart`, `zone_task_view_move_resize_test.dart` (including the new sibling-instance-untouched test), `zone_container_resize_handle_test.dart`, `zone_move_end_to_end_test.dart`, `zone_multi_task_selection_test.dart` — passed 30/30.
